# 架构

```
 浏览器
   │  HTTP / WebSocket（默认只接受本机访问）
 MakerMods Lab + 控制器路由 ──── 模型进程 ──── StarVLA / LeRobot
   │  本机 TCP + msgpack + 令牌        │
 Controller Service ◄──────────────────┘    相机进程 ──共享内存──► 录制器
   │  USB CDC，RAC-Link
 STM32 控制器 ── CAN1  reBot RS
              ── CAN2  reBot RS
              ── UART1 Star 主臂
              ── UART2 Star 主臂
              ── 急停回路和继电器
```

## 几条贯穿全局的决定

**主从同步在 MCU 上闭环。** 遥操作的数据不经过 PC，所以 PC 卡顿不会让跟随抖动。但 PC 不是可有可无的：控制器 500 ms（`host_timeout_ms`，可配置）收不到 PC 的消息，就会让所有机械臂进入保持，包括正在主从跟随的。没有上位机时，没人能监督运动。

**Controller Service 是 USB 的唯一持有者。** 其他进程，包括 LeRobot 代理、模型进程和 Lab，都通过本机 IPC 访问它。谁也不会绕过它直接发指令。

**所有运动只有一个执行入口。** 示教、回放、模型、干预和回零，最后都走 `Runtime._execute`。切换来源时控制代次（generation）加一，固件拒绝旧代次的指令，所以迟到的数据不会把机械臂拉回去。停止和只读消息不受代次限制，否则控制器一旦失步就停不下来了。

**协议只定义一次。** `tools/gen_protocol.py` 同时生成 C 头文件和 Python 代码，两边不可能写得不一致。

**固件核心不依赖硬件。** `firmware/core` 是可移植的 C，硬件相关的全部在 `rac_port.h` 的接口后面。同一份核心在 STM32 上跑，也在 `firmware/port/sil` 的仿真器里跑。仿真器按真实的帧和字节协议回应，并模拟总线时序，所以测试里跑的就是要烧进去的代码。

**校准跟着机械臂走。** 校准按序列号保存并带版本号，数据集记录每个 episode 用的版本。

## 固件的时序

单上下文协作式设计。中断只负责填环形缓冲，其余工作都在主循环里按 500 µs 的节拍调度。CAN 机械臂每 4 ms 服务一次，Star 每 8 ms 一次。

Star 舵机会累计圈数。主臂在绑定时松开并清零圈数，这和官方脚本一样。从臂不清零，因为它可能还在保持姿态，松开就会掉下来。两种情况都按校准范围的中点把读数折回同一圈；从臂发位置指令时不再更新圈数，并把指令加回当前圈，否则它会转一整圈回去。

## 三种增益

reBot 按用途用不同的增益，数值都来自上游在真机上用的配置：位置控制最硬；跟随主臂时用 Seeed 的软一些的增益，因为手的动作可能很突然；手扶时在实测位置附近留一个很弱的回路（kp 1.5，kd 1.0），靠重力力矩托住，从位置增益 0.5 s 渐变过去，进入时没有力矩突变。

滑块和末端拖动的目标先经过服务里的 jerk 限制（4 rad/s²，30 rad/s³），再送给固件，所以目标跳变时机械臂也是平滑起步。预录的轨迹本身已经平滑，不走这一层。

`rac_port_sync_pulse` 和 `SYNC_OUT`、`SYNC_IN` 引脚已经接好，但核心目前还不驱动它们：单板上的所有机械臂共用一个时钟，用不到。它们是为今后多块控制器互相同步留的。

## 数据

`LeRobotDataset` 只存对齐后的帧。原始时间线放在 `meta/rac/episode_NNNNNN/` 里，不会因为对齐而丢失任何样本。标注放在 `meta/rac/annotations.json`，改标注不会碰到样本数据。

时间对齐依赖 `rac_link.clock`：用 NTP 式的四时间戳交换估计 MCU 和 PC 的时钟关系，只取往返时间最短的那一半样本。录制完成后再对每个 episode 单独拟合一次 MCU 到 PC 的映射。

每个 episode 还记录设备配置、校准版本、控制来源区间，以及模型配置（调用方指定的，或者这一段里实际驱动过机械臂的模型）。

## 进程和故障

| 故障 | 行为 |
| --- | --- |
| 急停按下 | 硬件回路直接断开继电器线圈，固件检测到后进入急停状态，拒绝运动指令 |
| 主控复位 | 继电器栅极有下拉，继电器释放 |
| PC 或 USB 断开 | 超时后控制代次加一，所有机械臂保持，主从也停止；队列里的旧指令不会再执行 |
| 主臂读数一次变化超过 25° | 手做不到这么快，只可能是复位或圈数错误。上报 `LEADER_JUMP`，配对停止，从臂保持 |
| 模型进程退出 | 运行结束，上报 `policy_failed`，机械臂保持 |
| 相机取不到图 | 录制把该路相机标记为出错，并计入丢帧 |
| 电机通信丢失 | 上报 `MOTOR_LOST`。上电中的机械臂保持，其配对停止；主臂丢失时配对同样停止 |

继电器触点只有 G5V-2 的额定值，**不能直接切断 48 V 电机电流**，只能用来驱动外部的接触器或驱动器使能。详见硬件文档。

## 来自各上游项目的部分

Lab 的页面、数据集和会话流程保留，通过 `install_controller(app)` 以扩展的方式接入。上游文件总共只改了 35 行：`server.py` 安装扩展（`MAKERMODSLAB_NO_CONTROLLER=1` 可关闭），`sessions.py` 让机型把某类会话指向自己的页面，`tests/conftest.py` 让上游测试在不装扩展的状态下运行，前端的 `App.tsx`、`Launchpad.tsx` 和两个语言索引文件加入口。

`controller` 类型的机器人在 Lab 里能遥操作和录制，录出的数据集能在控制台回放。Lab 的回放和模型部署则会被明确拒绝并提示去控制台，因为它们的缓入按角度计算速度和容差，而这里的机械臂以弧度工作、由服务执行。校准同理：Lab 要求校准文件存在，所以目录里放了占位文件，真正的校准在服务里。动作缓冲改编自 EVA-Client。LeRobot 通过插件式的 Robot 和 Teleoperator 代理接入，StarVLA 按其 WebSocket 协议对接。reBot 和 Star 的真实 URDF 与网格随仓库分发。动作平滑、夹爪助力、显示滤波和增益来自 ReBot RS Digital Twin，主从方向来自 Seeed 的集成。完整清单见 [LICENSE_AUDIT.md](LICENSE_AUDIT.md)。
